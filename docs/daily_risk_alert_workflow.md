# Daily Inventory Risk Alert Workflow

## 1. Overview

The Daily Inventory Risk Alert workflow automates the generation and delivery of inventory risk alerts for the Perishables Network Planner.

The workflow runs on a scheduled basis, retrieves the latest inventory plan from the backend API, generates a risk summary, and sends an email notification when material inventory risks are detected.

The workflow is implemented using **n8n** and integrates with the deployed FastAPI backend.

The purpose of this automation is to reduce the need for manual monitoring of inventory plans and provide timely visibility into potential stockouts, expiring inventory, and warehouse shortages.

## 2. Workflow Architecture

The workflow consists of the following nodes:

1. Schedule Trigger
2. Login HTTP Request
3. Get Plans HTTP Request
4. Limit
5. Alert HTTP Request
6. IF
7. Send an Email

### Workflow Execution Flow

```text
Schedule Trigger
      |
      v
Login HTTP Request
      |
      v
Get Plans HTTP Request
      |
      v
Limit (1 item)
      |
      v
Alert HTTP Request
      |
      v
IF: alert_needed?
      |
      +---- True ----> Send an Email
      |
      +---- False ---> No email sent
```

## 3. Schedule Configuration

The workflow is configured to run once every day.

| Parameter | Configuration |
|---|---|
| Trigger | Schedule Trigger |
| Frequency | Daily |
| Execution time | 8:00 AM |
| Timezone | Asia/Kolkata |

The workflow is currently kept inactive and will be activated when the project is ready for scheduled execution.

## 4. Backend API Integration

The workflow communicates with the deployed Perishables Network Planner API.

**Base URL:**

`https://perishables-planner-api.onrender.com`

### 4.1 Authentication

The Login HTTP Request node authenticates with the backend using the configured login credentials.

The API returns an access token, which is used by subsequent HTTP Request nodes.

The token is passed through the Authorization header using the Bearer authentication scheme.

### 4.2 Retrieve the Latest Plan

The Get Plans HTTP Request node calls:

`GET /plans`

The backend returns the available plan runs in descending order of plan date and ID:

```sql
ORDER BY plan_date DESC, id DESC
```

This ensures that the most recent plan appears first.

The Limit node is configured to pass only one item. Therefore, the workflow processes the latest plan returned by the API instead of generating alerts for every historical plan.

### 4.3 Generate the Risk Alert

The Alert HTTP Request node calls:

`POST /plans/{run_id}/alert`

The plan ID is inserted dynamically from the plan returned by the previous node.

The endpoint evaluates the plan for inventory risks and returns an alert response.

The response includes:

- `run_id`: ID of the plan being evaluated
- `alert_needed`: Indicates whether an email alert is required
- `message`: Generated risk summary
- `verified`: Indicates whether the generated alert passed verification
- `source`: Indicates whether the message was generated by Gemini, a fallback template, or no alert was required

## 5. Risk Detection

The backend evaluates the plan using computed inventory facts.

The alert considers the following risk categories:

- Likely stockout risk
- Possible stockout risk
- Expiring inventory
- Store lines marked as warehouse short
- Warehouse shortage pools
- Warehouse shortage quantities

The alert decision is based on backend-computed values rather than an unrestricted LLM decision.

When risks are detected, the backend uses Gemini to generate a concise explanation based on the supplied facts. The generated response is verified before being returned.

If the generated response fails verification or the generation process encounters an error, the backend uses a predefined fallback message.

When no material risk is detected, the endpoint returns `alert_needed = false`.

## 6. Email Notification

The IF node checks the `alert_needed` field returned by the Alert HTTP Request node.

- **True:** The Send an Email node executes.
- **False:** The workflow ends without sending an email.

The email contains the risk summary returned by the backend.

### Email Configuration

| Parameter | Configuration |
|---|---|
| Subject | Perishables Planner - Daily Risk Alert |
| Body | Backend-generated risk summary |
| Format | HTML |
| Recipient | Configured email recipient |

The email body displays the alert message returned by the backend.

## 7. Security and Credentials

Credentials are configured separately in n8n.

The workflow uses:

- Backend API login credentials
- Gmail SMTP credentials
- Gmail App Password for SMTP authentication

Credentials should not be committed to the project repository.

The exported workflow JSON is stored in the project's `n8n` directory. Before committing the JSON, any sensitive values included directly in node configuration must be removed or replaced with placeholders.

## 8. Testing and Validation

The workflow was tested through manual execution in n8n.

### Test 1: Risk Alert

A plan containing inventory risks was processed.

The backend returned:

- `alert_needed = true`
- `verified = true`
- `source = gemini`

The IF node followed the True branch, and the email notification was successfully delivered.

### Test 2: No Risk Alert

A plan with no material inventory risks was tested.

The backend returned:

- `alert_needed = false`
- `verified = true`
- `source = none`

The IF node followed the False branch, and no email was sent.

### Test 3: Latest Plan Selection

The Get Plans endpoint was verified to return plans in descending order of plan date and ID.

The Limit node was tested and confirmed to pass only one item to the Alert HTTP Request node.

The alert request uses the plan ID dynamically rather than a hardcoded ID.

## 9. Workflow Deployment and Maintenance

The workflow is maintained in n8n Cloud.

The workflow JSON has been exported and committed to the project repository for version control and backup.

The workflow remains inactive until scheduled execution is required.

Before activation, the following should be verified:

- API credentials are valid.
- SMTP credentials are configured.
- The schedule and timezone are correct.
- The latest plan is available in the backend.
- The workflow executes successfully.
- The email recipient is correct.

When the workflow is activated, it will run daily at the configured time and send an email only when the latest plan requires an alert.

## 10. Limitations

- The workflow processes only the latest plan returned by the backend.
- If no plan exists, there is no plan available for alert generation.
- The email is generated from the backend alert response and does not independently calculate inventory risks.
- The workflow depends on the availability of the backend API and email service.
- The workflow is currently configured for daily execution and is not active.

## 11. Future Improvements

Potential improvements include:

- Adding configurable alert thresholds.
- Including a link to the plan dashboard in the email.
- Supporting alerts for multiple selected plans.
- Adding retry handling for temporary API or email failures.
- Recording workflow execution status for operational monitoring.
- Supporting configurable notification recipients.
